(*) NOTA SOBRE DELTAS NEGATIVOS — drift de reloj cliente vs AWS:
    El reloj de Windows local está adelantado ~500 ms respecto a UTC.
    Esto hace que el sent_at del cliente (10:47:13.455Z) parezca ser
    POSTERIOR al received_at de Lambda (10:47:13.037Z), generando deltas
    negativos. Es un artefacto de medición, no una latencia real.

    Los timestamps autoritativos (server-side, sin drift) son:
      - [EMERGENCY_RECEIVED] ts en Lambda (AWS server clock)
      - [EMAIL_SENT]         ts en Lambda (AWS server clock)
      - Gmail Date header     (Google server clock)


=== C) MEDICIÓN DE LATENCIA SERVER-SIDE (sin drift de cliente) ============

  Lambda recibió evento     : 2026-04-27T10:47:13.037Z
  SES aceptó el correo      : 2026-04-27T10:47:13.291Z
  Tiempo Lambda → SES accept: 254 ms   (lo que controla nuestra solución)

  Tramo final (SES → Gmail) : depende de la red de Google, típicamente
                              1-3 segundos. Se confirma en la bandeja de
                              erickcloud44@gmail.com con el header Date.

  Total esperado end-to-end : ~1.5 a 3.5 segundos
                              ≪ 15 segundos (puntaje completo de la rúbrica)

=== F) NOTA OPERACIONAL ===================================================

Si el reloj local de Windows está adelantado (como en este test), las
métricas server-side (Lambda, SES, Gmail Date) son las que valen para
la rúbrica. La k6 console muestra el sent_at del cliente para trazabilidad.

Para corregir el drift antes del demo final:
  PowerShell (admin): w32tm /resync /force

Ó usar una máquina con NTP sincronizado nativamente (Linux, macOS).
